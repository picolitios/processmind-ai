# Current state (2026-10-19)

## Implemented

The MVP business API is a modular FastAPI application with domains for identity, ingestion, audit, AI explanations, cases and analytics. A dedicated FastAPI identity process serves public auth and organization routes through nginx. PostgreSQL 16 hosts separate `identity` and `business` schemas in one database. Runtime roles can access only their own schema; an administrative credential is reserved for migrations and cross-domain reconciliation. Alembic owns schema changes. Separate import and model processes poll disjoint job types from the business `jobs` table. Audits are dispatched through an outbox publisher, RabbitMQ and an audit consumer in Compose; database polling remains a rollback mode. Docker Compose runs these processes with the database, API and UI; long-lived services have restart policies for local Docker-engine recovery. GitHub Actions runs Python, web, browser E2E, distributed-load and isolated RabbitMQ recovery gates. Existing API routes are versioned under `/api/v1` and audit creation returns 202 with a job ID. Existing regression and browser flows cover import through case resolution.

The audit engine is deterministic and stores findings with evidence. Ollama produces optional explanations; it does not determine audit findings. In Compose, business routes validate sessions, CSRF and active tenant membership through signed private identity requests without caching authorization decisions. Case routes also resolve assignee and author references through a bounded private identity lookup. Import deduplication uses a transaction-scoped PostgreSQL advisory lock keyed by tenant. Audit creation reads a locked audit-owned configuration row. Identity persists a durable settings command, calls the private audit-owner apply contract, and returns success only after confirmation; a dedicated identity reconciler retries outages. The shared-database write remains available only in rollback mode with an administrative credential. Business actions have their own append-only audit trail; Compose writes only there, while `dual` mode can retain a temporary legacy copy in `audit_events` for rollback. Case history reads the business table. Tenant-scoped tables use organization IDs and, where needed, composite foreign keys. The UI nginx container is the client entry point; CORS and correlation IDs live in FastAPI. Identity can be restarted independently and cannot read the business schema, but the processes still share one PostgreSQL instance and Python image.

The V2 copilot is integrated with normal and temporary chats, organization memory, approval policy, evidence citations and a local-model fallback. An operator-only command reports aggregate outbox, audit-job and RabbitMQ queue metrics with optional failure thresholds; no tenant data is exposed by that command. A separate Compose monitor samples these aggregates and signals stale or failed audit dispatch through container health. Business and identity requests and audit broker transitions emit allowlisted JSON records with the event's correlation ID.
Private authorization calls from business to identity carry the originating business request ID under the short-lived internal HMAC. Identity adopts that ID only after signature verification, allowing operators to follow an authorization failure across both process logs.

Business readiness in Compose requires both PostgreSQL and identity readiness because authorization depends on the dedicated identity process. The web healthcheck probes that route through nginx; broker health remains an independent monitor signal so a temporary broker outage does not reject a committed audit request.
The local deployment gate combines Compose health, Alembic head, runtime credential probes and the aggregate audit-dispatch snapshot without changing data. The documented release sequence uses a quiesced backup and isolated restore evidence.

## Risks and constraints

- The original database polling path is retained for rollback. The RabbitMQ path adds an event contract but still uses the shared job table and database; it is not yet a separately owned audit service.
- One database, migration role and shared Python image still couple identity and business operations. This is schema and runtime-credential isolation, not independent database infrastructure.
- Broker re-delivery after a consumer crash reclaims the audit job when no active transaction holds its row. A per-attempt token fences a previous consumer before it writes results; a locked row takes the delayed retry path. The one-hour lease remains for the database worker and for diagnosing jobs whose broker message is unavailable.
- Business readiness checks PostgreSQL and identity in Compose. The audit monitor provides a local broker/dispatch health signal, not external paging or retained time-series metrics. Correlated JSON records cover HTTP ingress and the audit broker path, but not full distributed spans or every process log.
- API, web, real RabbitMQ recovery, browser E2E and a small concurrent distributed-load sample run in CI. Browser E2E is also available for explicit local execution; CI runner timings do not establish production capacity.
- A quiesced local backup covers PostgreSQL and private uploads, with a manifest and isolated CI database and upload-volume restore checks. Backup scheduling, offsite retention and production recovery objectives remain open.
- `specs/decisions/0001-modular-monolith.md` correctly records the MVP decision. The new architecture request is an evolution, not a retroactive replacement.

## Reuse

The first increment reused existing contracts, database migrations, tenant enforcement, deterministic rules and the audit status endpoint. The remaining migration can focus on process and data ownership where justified.
